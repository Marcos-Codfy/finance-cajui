## Por que esta fonte importa para o Cajui

- O plano fixa "OWASP ASVS nível 2" como meta. Essa meta só é verificável se cada requisito L1 e L2 da **5.0.0** tiver status e evidência; é isso que vira o `docs/security/asvs-checklist.md` na Fase 5.
- A 5.0 reescreveu quase tudo: dos 286 requisitos da 4.0.3, só 11 ficaram iguais; o capítulo V1 Architecture sumiu; nasceram capítulos de Web Frontend, Self-contained Tokens, OAuth/OIDC e WebRTC. Material antigo baseado em 4.x (numeração `V2.1.1` = senha) **não serve**.
- A 5.0 criou "requisitos de documentação" (primeira seção de cada capítulo): a decisão de segurança tem de estar escrita para poder ser verificada. Encaixa no desenvolvimento spec-driven: boa parte do L2 se cumpre em `docs/spec/` e nos ADRs, antes de existir código.
- O ASVS cobre o backend e o que o navegador recebe. **Não cobre** o app Android, nem backup, DNS, CI/CD ou hospedagem, nem risco específico de LLM. Esses buracos têm de ser fechados com MASVS, Top 10:2025 e LLM Top 10.

### Níveis (definição da 5.0)

Os níveis são por prioridade (redução de risco x esforço), não mais por "testável em caixa-preta". **L1**: cerca de 20% dos requisitos (por volta de 70), primeira camada contra ataques comuns que não dependem de pré-condição. **L2**: cerca de 50% a mais; cumprir L2 = L1 + L2, aproximadamente 70% de um total de cerca de 350 requisitos em 17 capítulos; o padrão diz que a maioria das aplicações deve mirar este nível. **L3**: os 30% finais, defesa em profundidade e controles difíceis de implementar.

### Formato oficial da lista de requisitos

Na tag `v5.0.0`, pasta `5.0/docs_en/`, prefixo `OWASP_Application_Security_Verification_Standard_5.0.0_en`: `.csv`, `.json`, `.flat.json`, `.xml`, `.cdx.json` (CycloneDX), `.docx`, mais variantes `.legacy.*` com a estrutura antiga. O PDF fica em `5.0/`. Cabeçalho do CSV: `chapter_id,chapter_name,section_id,section_name,req_id,req_description,L`. O `req_id` vem como `V1.2.5`; o checklist converte para `v5.0.0-1.2.5`. Para o Cajui, **CSV** gera o Markdown e **flat JSON** serve ao script de conferência do CI.

## O que não se aplica, e por que

- **V10 OAuth/OIDC, V17 WebRTC, V4.3 GraphQL, V6.8 IdP, V7.6 sessão federada, V8.4.1 multi-tenant**: tecnologia ou cenário ausente.
- **V4.4 WebSocket**: N/A enquanto o chat com IA usar requisição HTTP comum. Se migrar para WebSocket, a seção volta.
- **V9 Self-contained Tokens**: N/A por decisão (D-ASVS-07).
- **V6.2 Password Security**: N/A somente se nenhum caminho usar senha. Basta a web ganhar senha para o bloco inteiro valer, inclusive checagem contra senhas vazadas (6.2.12).
- **V1.4 memória, 15.3.6 prototype pollution, 1.2.4 SQL, 1.2.6 LDAP, 1.2.7 XPath, 1.2.8 LaTeX, 1.3.8 JNDI, 1.3.9 memcache, 1.3.11 e-mail, 1.5.1 XML**: linguagem ou componente ausente.
- **V5.2/V5.3 upload e armazenamento de arquivo, 5.4.3 antivírus**: backend só recebe texto (D-ASVS-10).
- **3.3.x cookies**: N/A se a sessão for por cabeçalho `Authorization`.
- **Flutter Web**: 3.2.2 (renderização segura de texto) e 3.2.3 (DOM clobbering) quase não têm superfície, porque a interface é canvas; o que é HTML de verdade é o `index.html` e o DOM de semântica gerado pelo motor, que não recebe HTML vindo de dado.

## Pontos de atenção

1. **A autenticação planejada não fecha o 6.3.3 (L2).** `local_auth` só diz "o dono do aparelho passou na biometria"; nada liga isso criptograficamente ao que o servidor recebe. Em aparelho comprometido, o booleano é contornável e o token em `flutter_secure_storage` é o único fator. Para contar como dois fatores, a biometria tem de **destravar uma chave em hardware** que assina um desafio do servidor. Isso pede código de plataforma ou plugin específico além de `local_auth`; é decisão de Fase 4 com impacto em prazo.
2. **Web sem caminho de autenticação.** 6.1.3 exige documentar todos os caminhos e 6.3.4 exige força consistente entre eles. O plano só descreve o Android. Qualquer solução com senha reabre o V6.2 inteiro.
3. **"Segredos em variável de ambiente" não cumpre o 13.3.1 (L2)**, que pede solução de gestão de segredos "such as a key vault". A custo zero é desproporcional; tratar como exceção aceita, por escrito, com compensações. Dizer "ASVS L2" sem essa ressalva seria falso.
4. **16.4.3 (log em sistema separado) e 12.3.3 (TLS entre serviços internos)** são L2 e não cabem em uma VM única. Mesma saída: exceção documentada.
5. **4.1.2 contraria o padrão do Caddy.** O redirect automático de 80 para 443 é o comportamento certo para site e o errado para API, porque cliente mal configurado manda credencial em claro uma vez e o redirect esconde o erro.
6. **14.2.3 e a DeepSeek.** O ASVS fala em "untrusted parties". A redação de PII é necessária, mas não suficiente: o padrão exige que esteja **classificado e documentado** o que pode sair. Valor + estabelecimento + data formam perfil de consumo; o usuário único aceita isso, mas tem de estar escrito.
7. **11.2.1 (biblioteca validada pela indústria)** é difícil de defender em Dart puro. Registrar a escolha e o motivo; preferir implementação que delegue a biblioteca nativa consagrada, se existir.
8. **Desproporcionais para usuário único** (cumprir no mínimo ou aceitar exceção): 6.4.4 prova de identidade na perda de fator (aqui, acesso SSH é a prova); 7.4.5 e 7.5.2 gestão de sessões (baratos, mas são tela e comando a mais); 11.1.1 política de chaves (uma página resolve); 15.1.2 SBOM (barato no CI); 7.1.2 sessões simultâneas; 13.2.5 lista de saída no servidor web.
9. **Volume.** L1+L2 é cerca de 70% de aproximadamente 350 requisitos. Mesmo com os N/A, são mais de cem linhas a avaliar com evidência, para um desenvolvedor só. Por isso o checklist precisa nascer do CSV por script e ser preenchido junto com cada PR da Fase 6, não no fim.
10. **OWASP não certifica.** "ASVS L2" no README é autoavaliação. O capítulo de avaliação diz que ferramenta automática não verifica boa parte dos requisitos e recomenda revisão com acesso a código e documentação. Redação honesta: "autoavaliado contra ASVS 5.0.0 L2, com exceções listadas".
11. **Fora do ASVS por definição**: backup, DNS, CI/CD, hospedagem ("There is no such thing as scope for attackers", mas o padrão não os cobre). Backup diário, firewall, SSH por chave e o pipeline ficam a cargo do Top 10:2025 (A02, A03) e do runbook. Também **não há capítulo de LLM** na 5.0: prompt injection é coberto pelo LLM Top 10.
12. **HSTS com `includeSubDomains` e cookie `__Host-` dependem do domínio.** Custo zero implica subdomínio de terceiro (`vercel.app` na web; a API ainda não tem domínio definido no plano, e Let's Encrypt exige um nome). Resolver na Fase 4.
